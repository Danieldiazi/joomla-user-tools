# Joomla User Tools architecture

[Español](arquitectura.md) · **English**

[Back to the README](../README.en.md#development)

This guide describes the architecture of the `main` branch (not a fixed historical release). It is intended for anyone locating a rule, following a request or modifying a tool. For a shorter reading path, see the [developer onboarding guide](development.en.md). Update this guide whenever flows, persistence or guarantees change. Usage instructions are in the [README](../README.en.md) and [FAQ](../FAQ.en.md).

**Standalone bulk account creation**: `BulkcreateController`, `BulkcreateModel` and `BulkRegistrationList` implement a create-only flow. The parser retains line numbers and optional names and resolves groups on the server. An operator-owned, single-use preview includes a group fingerprint; the client submits only selected rows and email values, with a typed count of selected rows. Each creation rechecks username, email, permissions and group and reuses `Registration::create()`, `AccountMailer` and `ActionLogger`, with resumable batches and no persisted temporary passwords. Existing accounts are never blocked or updated. Usernames under 2 characters, which Joomla's user table rejects when saving, are flagged in the review here and in group synchronisation, and stop a Compare selection before anything is blocked.

The 5,000-account limit is enforced **after** filtering by group, status, visits and protected-account eligibility, not across all reset-required users. ID-keyset pagination and bounded chunks avoid loading the whole user table at once. **SSO conversion:** `SsoModel` creates a one-use review of accounts with `requireReset = 1` and `AccountProfile::fingerprint()` snapshots. `SsoConversionPlan` filters by groups and descendants, blocking and visits, excluding protected accounts. Only previewed IDs can be selected via `InactiveSelection::decode()`. Resumable 20-account batches call `SsoAccountConverter`, which loads a fresh Joomla User, revalidates the reset flag, identity, groups, status, visits and permissions, rotates the local password with `User::bind()` and `save(true)`, terminates sessions and audits without secrets. Cleartext passwords are transient in the Joomla User object and are never stored in session or shown.

## 2. Following a manual operation

### Example: deleting inactive accounts

1. Joomla displays the delete view. DisplayController requires the view permission; [Delete/HtmlView](../admin/src/View/Delete/HtmlView.php) obtains the draft and groups from the model and prepares the template.
2. On search, [DeleteController::search()](../admin/src/Controller/DeleteController.php) checks the token and usertools.delete permission. DeleteModel::search() validates the period, saves options and calculates candidates using InactivityPolicy, Exclusions and recent sessions.
3. The model stores a session preview: offered IDs, UTC cutoff, exclusions, status filter, settings signature, identity, nonce and expiry. It redirects to review.
4. DeleteModel::getReview() queries candidates again and only shows accounts offered in the preview. It does not add accounts that have since become eligible.
5. The browser submits selected IDs as JSON. DeleteController::delete() checks token and permission again. The model validates the preview, membership of the IDs, confirmation checkbox and typed count, required even for one account.
6. The model consumes the preview before writing. It recalculates eligibility; AccountDeleter reloads each account, checks protection and criteria, and calls User::delete(). Joomla dispatches its user-plugin events.
7. Each successful deletion is passed to ActionLogger. The model collects deleted accounts, errors and the skipped count, stores the temporary result and the controller redirects to the result screen.

### Differences in other tools

- **Comparison (explicit blocking selection #84):** the server offers missing-account `ids` in an operator-bound, expiring single-use preview with a nonce. The browser starts with **no block checkboxes selected** and submits `selection_ready=1` and a JSON array of `selected` account IDs, independently of `registrations` (new accounts). `CompareModel::apply()` rejects missing readiness and duplicate/foreign IDs via `InactiveSelection::decode()`; it never interprets an absent selection as all offered accounts. Reinforced confirmation (`confirm_count`) counts **selected blocks only**, with account creation validated separately. Only selected accounts that still qualify enter the `block` queue; only actual blocks are logged and may enter the reversible batch. Unticked accounts remain active and are reported as `unselected`, not as block errors or undoable blocks. The visible-row select-all checkbox derives its state from the currently visible rows without discarding hidden selections. Selected accounts are revalidated at execution; exclusions and protections remain enforced.
- **Comparison:** CompareModel calculates missing and unknown usernames. A changed set offered for blocking requires a new review. It validates the entire account-creation selection before blocking or creating; creation also requires usertools.create.
- **Account creation:** CompareModel temporarily disables the Joomla user plugin's email and restores its configuration in finally. Registration creates accounts in Registered; AccountMailer sends the link, a temporary password is returned (with a forced change at first login) or, in single sign-on mode, nothing is sent or shown: nobody knows the random password and no change is required. Each creation is written to the action log as soon as the account exists.
- **Batched application:** when applying, CompareModel consumes the preview and stores a job in the session with the IDs to block and the usernames and emails to create, never passwords. `step()` processes accounts for `Settings::batchSeconds()` seconds (8 by default, counted from the start of the request, and at least one account), and the first batch runs in the apply request itself. The progress screen asks `compare.step` for the rest; it checks the token and the permission and answers in JSON, and temporary passwords travel only in the response of the batch that created them. The job is saved after each account (a creation leaves the queue as soon as the account exists), so a request that is cut off repeats nothing when continuing; before creating, each batch checks `usertools.create` again and that the Registered group still exists without administrator access. `discard()` ends the job and leaves the rest untouched. There can be only one job per session and it belongs to whoever started it.
- **Temporary passwords:** [CompareController::apply()](../admin/src/Controller/CompareController.php) renders the result directly in the application response when passwords are present. The session copy is redacted and cannot recover them on reload.
- **Inactivity review:** InactiveModel uses explicit account selection and AccountBlocker. It skips blocked accounts and recent sessions. Accounts no longer meeting criteria are not replaced by others.

## 3. Following the scheduled task

The plugin's blockInactive() method receives parameters and task identity from the scheduler:

1. Loads the component and builds services. Creates a report before changing accounts; blocking does not start if the report cannot be written.
2. Uses Operator::system(): a visitor triggering the scheduler does not become the operation's actor.
3. Classifies enabled accounts, protections and omission reasons. Removes candidates with recent sessions.
4. MassBlockGuard compares candidates with enabled accounts. Exceeding the limit blocks nothing in real mode; dry-run mode reports the excess.
5. Simulates or calls AccountBlocker to revalidate and block each account. Saves progress every 50 processed accounts in the real-operation loop.
6. Finalizes the report and applies retention. Returns success or failure to the scheduler. A report-update error also causes failure.

Reports and the action log are separate evidence sources. A dry run does not create real blocking actions in the log.

## 4. Where data lives

| Data | Location and lifetime |
|---|---|
| Manual draft | Session, under tool-specific keys. Preserves input for editing; it does not have the preview's separate 15-minute expiry. |
| Preview | Session; 900 seconds, tied to the actor and a nonce. Relevant settings are checked through a signature. Consumed before application. |
| Manual result | Session; 900 seconds, tied to the actor. Temporary passwords are removed from the stored copy. This is not general persistent history. |
| Batched manual job | Session, owned by the operator; comparison, account creation and other resumable operations checkpoint per account. Losing the session may prevent continuing the pending work; completed changes remain. |
| Undo-block batches | Dedicated manual and scheduled block-batch reports stored through `ReportStore` under the log directory. They allow reviewing a subset of blocks still eligible for undo; they are not a general log of all operations. |
| Manual options | Component parameters in #__extensions, through SettingsStore. Shared across the site, with separate keys per tool. Searching can also save options. |
| Scheduled parameters | Each Joomla task's configuration; exclusions are independent of manual tools. |
| Accounts | Joomla user tables and API; blocks, creations and deletions use the API to run events. |
| Action log | Joomla's log, through ActionLogger. Contains no passwords. Writing may fail without stopping the account change. |
| Scheduled reports | usertools-reports subfolder of the logs directory. PHP files with a denial header and JSON body. Retention is configured in Options and applied when tasks finish. |
| Temporary password | Generated in memory and shown in the creation response. Joomla retains the authentication hash, not the clear-text password. |

### Session contracts: preview, job and result

These three states are not interchangeable; each tool model documents its business fields in PHPDoc. `ToolStateTrait` supplies only common metadata and validation:

| State | Metadata or fields | Meaning and limitation |
|---|---|---|
| Preview | `actor` (operator ID), `nonce` (random token), `expires` (Unix seconds) | Owner and expiry are checked; the controller/model also verifies the submitted token and tool-specific conditions. Consumed **before** any write. |
| Resumable job | `actor`, pending queues, original total and accumulated outcomes | Held in the operator's session. Each processed account produces a checkpoint; it is neither a transaction nor a way to roll back earlier changes after interruption. |
| Temporary result | `actor`, `expires` and tool-specific outcomes | A 900-second display snapshot. **Not** persistent audit history and not a replacement for the action log. Never holds temporary passwords. |

**Comparison** (`CompareModel`): the preview stores `names`, offered block `ids`, `unknown` names and an exclusions `signature`. The job carries `block` and `create` queues, a fixed `total`, and `processed` as completed attempts rather than successes. `blocked`, `created` and `errors` accumulate outcomes; `blockErrors` separates failed blocks from omissions/protections. The result distinguishes `skipped` (offered candidates not blocked) from `discarded` (pending operations explicitly abandoned). `batch` may refer to a **separate** persistent undoable-block report. Newly created passwords are present only in the immediate response of their creation step, never the stored job or result.

**Anonymization** (`AnonymizeModel`): the preview associates reviewed account `ids` with `fingerprints` and a `selected` subset; each step checks fresh account data again. `pending` maps remaining IDs to fingerprints while `total` stays fixed. `done` collects anonymized identities, `cleaned` cleanup-only retries, `partial` pending or unverifiable cleanup, `errors` failures, and `skipped` accounts not processed because of changes or conditions. On completion the temporary result exposes `anonymized`, `cleaned`, `retryCleanup`, `partial`, `errors`, `skipped` and `total`; it does not imply deletion outside its documented scope.

**Maintenance rule:** whenever session fields, their consumers or result states change, update the owning model's PHPDoc, this section and its translation. Array shape documentation never replaces real-time checks.

ReportStore validates file IDs and writes through a temporary file followed by a rename. The report's version property identifies its format; it is not the extension version.

## 5. Rules every change must preserve

- Check permissions per view and action, and CSRF tokens for change requests. Component access requires core.manage; tool permissions are in [admin/access.xml](../admin/access.xml).
- Preserve Super User and manual-operator protection. Non-Super Users cannot block or delete accounts with administrator access.
- Revalidate each account before changing it. A preview does not guarantee that its state remains unchanged.
- Apply only accounts offered and selected according to the flow. Never silently expand a review.
- Consume the preview before writes. This prevents reuse; it does not make the whole operation transactional.
- Keep dates in UTC and use a strictly earlier-than-cutoff comparison; use registration dates when including never-logged-in accounts.
- Use Joomla's API for changes and preserve plugin events.
- Do not persist or log clear-text passwords, or return plugin diagnostics that could contain them.
- Preserve template escaping, translatable text and non-cacheable sensitive responses.
- Preserve initial dry-run mode, the scheduled safety limit and mandatory typed confirmation for deletion.

## 6. Partial failures and current limits

Operations are not atomic: changes already applied remain if a later account fails. Services turn certain failures into per-account results; an unexpected interruption may prevent the manual summary from being saved.

ActionLogger discards exceptions so audit failures do not stop an operation. A changed account therefore does not guarantee a corresponding log entry. Task reports have checkpoints and may also remain incomplete if execution stops between saves.

Temporary manual results are not a complete persistent per-account history. Scheduled reports retain actions and protections in detail, and summarize omissions by reason. Manual block batches are persisted for «Undo blocks», but not all manual operations share a common identifier or unified durable log.

These are limits of the current implementation, not guarantees of complete auditing or automatic recovery. A future persistent history must explicitly address these cases.

## Category navigation

`Navigation` centralises view permissions and the category/tool catalogue. `DisplayController` validates view and category access; `Home/HtmlView` filters the home screen with the same catalogue, and the dashboard module reuses it for shortcut names, order and grouping. The `report` detail belongs to the reports category. `ViewTrait` adds a category return link while keeping Home.

The manifest installs Home and five category submenu entries, by purpose: look up (read only), manage accounts, manage groups, automation and deletion. `NavigationTest` checks that the look-up category only has read-only tools and the others have none. The `system/usertools` plugin listens to the public `onPreprocessMenuItems` event, checks current permissions and removes only forbidden User Tools links. It marks the active path through native menu nodes without changing link destinations. It also runs outside the component and does not depend on Atum DOM or CSS.

Permission to configure tasks is checked on `com_scheduler`; moving groups keeps global `core.admin`. The plugin does not replace controller checks. The package enables it once and records the marker on that extension; subsequent updates preserve an explicit disable. The builder, ZIP verification and release include the system plugin. Integration tests cover installation, upgrades, permissions, active paths and uninstallation; captures use the disposable Joomla site.
